## 1. 文档效力与验收原则

### 1.1 约束级别

- **必须**：发布验收门槛；本文件所有带需求编号的表格行默认属于“必须”。
- **建议**：可以采用其他实现；不单独构成验收失败，明确以“建议”标注。
- **禁止**：违反即验收失败，不以视觉效果、开发成本或测试数量抵消。
- **P0 缺陷**：泄露隐藏信息、改变规则/结算、错误提交、丢失有效会话、无法完成主流程、客户端崩溃等阻断问题。
- **P1 缺陷**：违反本规范的必要布局、可读性、操作、兼容性、性能或可访问性要求。
- **P2 缺陷**：不影响要求达成的局部视觉细节或建议项；仍应记录处置。

**最终通过条件：所有必须项有证据且通过；P0、P1 未解决项为零。不得用整体评分或“基本完成”代替逐项结论。**

### 1.3 度量与证据定义

本文尺寸均为 CSS px，比例以浏览器内容视口计算；浏览器缩放默认 100%。颜色为 sRGB。时间使用毫秒或秒，除特别说明不含服务器/公网等待。截图必须来自真实实现，不用设计图冒充运行截图。

验收证据类型：`V` 浏览器截图与布局测量；`I` 真实交互；`A` 自动化断言；`N` Socket/HTTP 网络证据；`P` 性能记录；`R` 源码与资源审查。一个需求可组合多种证据。

需求表中的编号为主键。后文 `TC-*` 是验收场景，不替代需求逐项检查；同一场景可同时验证多个需求。

## 2. 改版目标、范围与边界

### 2.1 预期变化

新版将游戏统一为“简约、高级的科幻舰队作战中枢”：海域沙盘、舰队健康、指令编排和战术记录构成同一套控制台。**简约高级感约束常态界面，科技感通过海域沙盘、精准交互和关键事件释放。** 优先用比例、排版、留白、低对比材质和一致反馈建立品质，再使用局部光效与过程动画表达科技感。

开发中的取舍顺序为：**玩法与信息正确 → 读得清、操作明确 → 信息精简与视觉秩序 → 材质和科幻装饰**。发生冲突时遵循这个顺序；不能为画面“干净”隐藏关键状态，也不能为科技感增加无决策价值的常驻面板、假指标或重复提示。简约的对象是重复与装饰，功能、信息权限和可访问性仍完整保留。

这次是整体呈现与交互组织更新：覆盖从进入游戏到复盘的完整链路，不限定为战斗页换肤。**界面结构、旧类名、组件拆分可以改变；游戏规则、协议语义、权限和数值不改变。**

| 编号 | 要求与通过条件 |
| --- | --- |
| SCOPE-01 | P01 进入、P02 等待、P03 部署、P04 掷骰、P05 正常对战与最终齐射、P06 结算复盘、T01 五章教程、全部设置与异常覆盖层均纳入同一设计系统。 |
| SCOPE-02 | 保留双人联机、三人 FFA、三档 1v1 人机、三个地图档位及全部十种行动。不得用“后续接入”的假按钮替代现有功能。 |
| SCOPE-03 | 保留三套主题、五种强调色、自动/高画质/流畅、减少动画、音效与音乐独立设置及原有本地偏好。 |
| SCOPE-04 | 不新增账号、排位、商城、聊天、观战、匹配队列、三人人机、舰艇移动、新武器、主动跳过回合等产品功能。视觉素材中出现这些概念，不构成功能授权。 |
| SCOPE-05 | 桌面正常战斗有新的舰队区、中央战场、指令区和统一指令台；旧驾驶舱框架、旧多代 CSS 类和旧底部五栏不能原样搬入后仅调整颜色。 |
| SCOPE-06 | 新版首屏能直接辨认当前阶段、回合归属、连接状态和下一步操作；必要状态不依赖悬停、特效播放或打开说明才能获知。 |
| SCOPE-07 | 服务端权威、伤害/弹药/瘫痪/胜负、地图派生参数、AI 策略与权限不变。因 UI 改造需要改动共享代码时，须证明行为等价。 |
| SCOPE-08 | 所有最终交付内容以真实数据驱动；战斗界面不得把设计演示的假 HP、在线数、任务、雷达信号或敌舰轮廓混入正式对局。 |

### 2.2 保留的玩法事实

这些事实用于设计检查，不另造一套战斗实现：

| 项目 | 应继承的行为 |
| --- | --- |
| 舰队 | 七类、八个作战单位；两艘摩托艇独立；诱饵是部署物 |
| 地图 | 10/12/15；行 A～J/L/O；列 1～10/12/15；逻辑坐标不因显示缩放改变 |
| 航母 | 5/6/8 格四向连通，HP 同为 5/6/8；不固定为直线 |
| 部署/行动/重连 | 180 秒 / 90 秒 / 120 秒；均以服务端状态为准 |
| 首回合 | 每人首个正常回合强制雷达 |
| 三人 | 一次行动同一目标同步全部仍在局敌方；资源和行动方自损只结算一次 |
| 最终齐射 | 秘密选己方鱼雷，全员提交后同时结算，最后比较航母 HP |
| 重复攻击 | 除驱逐舰共享已用坐标限制外，按原规则允许；每单位格一次伤害资格 |
| 直升机 | 己方两艘驱逐舰沉没后解锁；整行/列；对航母单次最多 2 点伤害 |
| 舰艇位置 | 部署锁定后不移动；航迹仅作视觉材质，不能表现为位置变化 |

## 3. 视觉方向与设计系统

### 3.1 科幻控制台的明确构成

| 编号 | 要求与通过条件 |
| --- | --- |
| VIS-01 | 主视觉由“深空海军蓝底、低频海面、干净的半实体控制面板、单一强调色和少量语义色”构成；所有页面共享材质与组件语言。默认离子青表达指令，琥珀/紫色仅用于有明确含义的状态，不作每个面板的常驻配色。 |
| VIS-02 | 主战场为视觉中心；在正常待命截图中，装饰边框、标题、背景舱壁不得比目标框、己方回合或主执行按钮具有更强的持续发光/闪烁。 |
| VIS-03 | 提供三类可辨识表面：背景环境、工作面板、浮动交互层。优先用实体明度、间距和细边界表达层级；阴影仅用于真实抬升的浮层，不以大面积玻璃模糊、多重阴影或连续描边替代布局。 |
| VIS-04 | 小切角、端点、刻度仅可选作局部科技细节，每个面板最多选择一种；控制面板默认不叠装饰扫描线与电路纹，正文区域不铺装饰纹理。功能性的地图坐标/扫描不受此限制；点击区不因切角缩小。 |
| VIS-05 | 战斗环境可沿用真实海面与现有舰体；新版主控制台不使用整张旧驾驶舱背景承载所有功能框。旧舰桥图只可作低对比远景或非核心场景。 |
| VIS-06 | P01、P03、P05、P06 至少在布局、标题、面板、按钮和状态组织上完成统一重构；不能保留整页旧样式造成新旧两套系统并存。 |
| VIS-07 | 装饰文字只限短编号/刻度等非决策内容。行动、坐标、倒计时、资源、错误等必要信息必须使用 HTML 可访问文本，不烘焙在图片里。 |
| VIS-08 | 科技动效必须对应连接、选择、扫描、结算、切层等真实状态；不得展示会被理解为真实情报的随机敌舰、虚构目标数或假雷达点。 |
| VIS-09 | 光效限于当前目标锁定、关键操作状态和真实战斗事件；待命面板、普通卡片、普通标题默认无外发光。主按钮靠清晰底色与对比度突出，hover 可轻提亮，不要求发光。 |
| VIS-10 | 深/浅/暮三套主题均须完整覆盖所有页面与覆盖层；浅色主题不能只改文字、留下不可读的深色输入和科幻纹理。 |
| VIS-11 | 胜负、受击、资源耗尽、禁用、选中、私人推断具有不同形态或文字；不得把所有特殊状态都做成同一青色描边。 |
| VIS-12 | 输出一张组件规范页和 P01/P03/P05/P06 的关键视口视觉参考，保存本地源文件或可查看图片；参考应能展示本文尺寸与状态，而非仅有氛围图。 |

### 3.4 简约高级感：开发与验收约束

这里的“高级感”指清晰的视觉秩序、准确的比例、精细的排版、稳定的组件和有节制的反馈。开发时先完成无光晕、无粒子、无纹理的静态工作界面，证明层级与操作成立，再加入必要科幻效果。纯静态截图和流畅模式也应呈现完整的设计品质。

| 编号 | 要求与通过条件 |
| --- | --- |
| PREM-01 | 简化不得损失关键事实：回合、时间、连接、行动、目标、实际影响方、成本/风险与错误仍按相应要求可见。遇到拥挤先去重复、重排或渐进展开，不缩字、隐藏关键状态或移除功能。 |
| PREM-02 | 每类信息指定主展示位置：回合/时间在状态栏，单位 HP 在舰队区，行动可用性在指令区，当前目标与提交在统一指令台。其他区域只保留必要的关联提示，不整块复制同一摘要。最终执行摘要为避免误操作保留必要信息，不算无意义重复。 |
| PREM-03 | 活动工作区内，可见实体卡片/面板的嵌套最多两层；同一分组内部优先用间距、标题或细分隔线组织列表，不出现“面板包卡片包小卡片包按钮框”的多重外框。抽屉/对话框作为新的活动容器单独计算，不把背景遮罩算作一层。 |
| PREM-04 | 普通常态控件采用中性色表面与一种用户强调色；语义色只在相应状态或事实图形出现。战场多种合法状态、舰体原色和主题选择预览可同时存在，不为凑色彩数量改变其意义。 |
| PREM-05 | 普通面板/卡片最多一层 1 px 外边界，内部不再叠完整双框、金属压边或浮雕边。焦点、当前目标和必要对比度使用的双描边保留，不能混同为装饰冗余。 |
| PREM-06 | 全局圆角默认统一为控件 8 px、卡片/工作面板 12 px、对话框/抽屉 16 px；同类组件不自行创建其他半径。若采用科技切角，仅用于选定的一级面板、深度 2～4 px，每面板不同时叠圆角与切角两套装饰。 |
| PREM-07 | 使用同一布局网格对齐标题、字段、列表与操作；组内间距 8～12，组间 16～24，文字标题到解释 4～8。空间不足切换布局，不压缩所有留白。地图占位、触控间隔及第 4 节空间规则优先。 |
| PREM-08 | 常规界面字体字重集中使用 400/500/600 三档；正文/说明不全部加粗。不用扩大字间距、额外描边、发光或多重阴影塑造“科幻字”；品牌图形与必要坐标强调单独处理。 |
| PREM-09 | 图标只用于识别动作、舰种或状态；普通卡片不额外配置无语义徽章、角标、伪编号、英文小标题和进度条。相同语义的图标、文字、徽章不在一行连续重复三次。 |
| PREM-10 | 单位列表默认展示名称、HP、关键状态；资源明细、规则长说明和历史信息渐进展开。存在瘫痪、耗尽、解锁条件或自损风险时，其影响当前决策的说明必须及时可见，不能藏到 hover 或深层帮助。 |
| PREM-11 | 行动区优先展示可用行动；受限/耗尽项可使用紧凑分组，并可一步展开查看全部十项与原因。合并的是展示密度，不能把暂不可用功能删除或造成状态变化后找不到入口。 |
| PREM-12 | 常态控制面板区域不播放装饰循环、扫描线、进度脉冲或粒子；海图最多一个主要持续环境动画层，其余环境叠层静态。与真实事件绑定的短时扫描、攻击与切层动画按第 20 节执行，仍可具有明确表现力。 |
| PREM-13 | 文字承载区采用平静的纯色/近纯色背景；海面、纹理、远景不得穿透到行动说明、表单、计时和日志正文形成高频干扰。必要半透明面板须有足够实体底色。 |
| PREM-14 | 入口、状态切换与反馈使用一致的时长、缓动与位移尺度；不因组件不同叠加弹跳、翻转、扫光等各自独立的动效语言。用户连续操作时可被新状态打断，不能排队演完装饰才响应。 |
| PREM-15 | 在设计交付中提供“信息保留/合并/展开、装饰移除/保留”的页面清单及静态/事件态对照图；逐项解释每个常驻区域和可见装饰的作用。没有用途的重复元素应移除，不能用“高级/科技”作为唯一保留理由。 |
| PREM-16 | 验收同时检查无动画常态、事件态、流畅/减少动画和浅色主题。常态必须清楚克制，事件态可以有更强局部表现，但不能破坏文字、焦点和目标；不能只选特效峰值截图证明完成。 |

**具体开发默认值：** 使用现有第 3.2 节色板建立实体表面；普通面板 `box-shadow: none`、单层细边框；只给浮层配置一档柔和阴影。按钮以底色/边界/明度表示主次，选中行使用一处侧标或底色，默认不同时添加光晕、角标、粗边和复杂纹理。所有半径、边界、阴影和动效从共享令牌取值，不在页面内临时调出另一套视觉体系。

### 4.3 滚动与浮层规则

常规页面允许内容纵向滚动，顶部不必强行占满屏。正常桌面对战由工作区控制高度；舰队列表、行动内容、日志各有自己的滚动容器。不得在同一方向叠三层滚动区域。抽屉打开后背景不滚动，关闭时恢复原位置。

浮层从低到高统一为：环境 → 地图与面板 → 粘性工具 → 下拉/提示 → 抽屉遮罩 → 抽屉 → 确认对话框 → 断线/恢复阻断层。Toast 不盖住确认与关闭按钮，断线层可以取消或替换已失效确认。

### 10.2 地图状态叠加优先级

从底到顶：海域环境 → 网格/轴 → 合法范围 → 己方单位或依法可见的历史 → 侦察/私人注记 → 当前目标 → 一次反馈特效 → 不挡操作的坐标标签。

“从底到顶”规定视觉解释优先级，不要求具体 DOM 顺序。目标轮廓在爆炸出现时仍可识别；中性执行动画不得临时把未知格改成命中/未命中。残骸、诱饵身份、瘫痪只出现在有权限的己方图和结束后复盘。

## 11. 行动编排与提交状态机

### 11.1 新版确认模型

**本次明确改变旧版选点即弹模态框的交互。** 正常战斗采用常驻指令台完成最终确认：选行动、选点后，摘要展示行动/目标/影响方/成本/风险；玩家按“确认执行”才发请求。点击地图不会自动提交，也不自动弹阻挡地图的确认框。

手机选点后可展开非阻断指令摘要；必须允许回到地图改点。投降、清空、离开等危险操作仍用独立确认对话框。正常攻击不叠两次相同含义的确认。

```text
待命 → 已选行动 → 已选目标 → 提交中 → 等待安全状态同步 → 完成/清理
          ↑         │          ├→ 可确定拒绝：解释并保留仍合法的草稿
          └─改行动──┘          └→ 结果未知：同步/同 actionId 重试
任意草稿态 → 服务端回合/阶段/来源失效 → 禁用提交并清理失效草稿
```

| 编号 | 要求与通过条件 |
| --- | --- |
| CMD-01 | 未选行动时提示“选择行动”；已选行动无目标时提示具体选点方式；有目标时显示准备执行摘要，不以含糊“等待指令”覆盖当前真实状态。 |
| CMD-02 | 地图选中目标只更新本地草稿；唯一主执行按钮才触发 `action:submit`。双击格子、长按、Enter 聚焦格子均不能绕过最终执行。 |

## 20. 动效与音效编排

### 20.1 动效预算

| 动效 | 标准时长 | 允许表达 | 减少动画/流畅回退 |
| --- | --- | --- | --- |
| 按钮/卡片交互 | 100～180 ms | hover、选中、聚焦 | 无位移或≤100 ms 透明度 |
| 抽屉/对话框 | 180～240 ms | 单轴位移≤24 px、淡入 | 直接显示或≤100 ms 淡入 |
| 页面切换 | 160～240 ms | 轻淡入，内容立即可操作 | 直接显示 |
| 目标锁定 | 160～260 ms，一次 | 准线/边界收敛 | 静态高亮 |
| 切视层 | 300～820 ms | 声呐/下潜/上浮过渡 | ≤100 ms 或无过渡 |
| 雷达/探测 | 700～1400 ms | 按已知区域的扫描过程 | 静态区域与文本 |
| 攻击过程/结果 | 总占用≤3600 ms | 按公开权限的过程与结果 | 短静态反馈，事实保留 |
| 胜负 | 600～1600 ms | 边框/徽章/局部粒子 | 静态结果 |
| 海图可选待命环境 | 低频周期≥6000 ms | 最多一个主要非情报环境动画层；控制面板不循环装饰扫描 | 停止 |

| 编号 | 要求与通过条件 |
| --- | --- |
| FX-01 | 所有动效遵守上表预算；长于 240 ms 的过渡不阻止普通按钮/地图操作。服务端倒计时不等待动画结束才显示。 |
| FX-02 | 同时最多一个主要战斗过程特效；新结果到达时结束/替换旧主效果，不把历史爆炸队列积压到下一回合。 |
| FX-03 | 效果层在≤3600 ms 后移除，监听器/计时器清理；切页、结束、离开立即清理，不产生游离 DOM 或旧声响。 |
| FX-04 | 不对整个地图持续透视/旋转/缩放，不用镜头震动移动点击目标。允许局部轻震，但减少动画时完全关闭。 |
| FX-05 | 屏幕无每秒超过 3 次的高对比闪烁；核弹表现局部受控亮度，不用全屏纯白连续闪屏。 |
| FX-06 | 音效由有效本地操作或已确认事件触发；重复渲染、重连快照、切图不重复播放历史效果。最大效果并发仍为 12。 |
| FX-07 | 隐藏武器使用固定中性动作音与过程动画，不依据隐藏命中分支变化；侦察阳/阴性反馈只依据该玩家合法结果。 |
| FX-08 | 新音效与既有音乐、合成回退兼容，用户关闭效果后无残留循环；切音乐/效果音量不互相影响。 |
| FX-09 | 高画质可有海面高光、泡沫、焦散与少量颗粒，默认静态叠层，遵守 PREM-12 的持续动画数量限制；不要求为每种素材增加独立循环。流畅模式关闭非必要连续层、模糊、大阴影和粒子，只保留事实与必要交互。 |
| FX-10 | 不在高/流畅模式之间改变公开信息量；截图/DOM 对比应体现相同坐标、状态和可操作性。 |

## 23. 性能与运行质量

以下是**新版应达到的验收预算**，不是声称当前版本已达标。基准机器和浏览器在性能报告中固定记录，前后对比使用同一环境、同一数据和同一缓存条件。网络等待与客户端渲染耗时分开统计。

### 23.1 参考采样协议

本节正式采样由独立复核执行者负责；Astra 开发阶段遵守预算、处理明显卡顿，并提供可复验场景与现有日志，不独自承担整套性能复核。

1. 桌面：当前开发 Windows 主机，记录 CPU、内存、GPU、OS、浏览器版本；视口 1366×768 与 1920×1080。
2. 手机压力：390×844，浏览器设备模拟、CPU 4 倍减速；这只能作为模拟数据，不能冒充真机结果。
3. 真机体验：至少一台实际手机浏览器完成部署、平移、选点、执行、抽屉、横竖屏与音频交互；记录型号/系统/浏览器。若测试设备不可用，列为未测，不计最终全通过。
4. 每次先预热一次，至少 30 次有效交互取 p95；页面加载至少 5 次冷缓存采样，报告中位数和最差值。
5. 性能场景使用 15×15 三人安全快照、100 条日志和全舰队状态；同时记录高画质与流畅模式。

| 编号 | 要求与通过条件 |
| --- | --- |
| PERF-01 | 纯本地选择/切换的可见响应 p95：桌面≤100 ms，4 倍 CPU 模拟≤200 ms；从输入事件到下一次有正确反馈的绘制，不把 Socket 往返计入该项。 |

### 25.3 组合策略：避免遗漏，也避免无意义全排列

| 集合 | 最低覆盖 |
| --- | --- |

| UI 视觉 | P01/P03/P05/P06 在 VP03、VP06、VP09、VP12 下三主题；P02/P04/T01/设置/错误至少 VP03、VP09 |

“三地图×三模式”中的人机是固定双人；禁止为覆盖矩阵构造三人人机。“完成一局”须经过真实结算，允许明确标注的投降结算验证流程；攻击获胜和最终齐射各有独立用例，不得全部用投降代替。

### 25.4 截图规范

1. 固定视口、主题、强调色、地图、角色、阶段、选中状态、数据种子与时钟。
2. 普通基线截图停在稳定帧；动态效果另以固定时间点截图或视频验证，不用随机帧做像素回归。
3. 每张图在清单登记：场景 ID、需求/TC、视口、浏览器、主题、质量、输入方式、代码提交、日期。
4. 页面顶/底、抽屉末尾、确认摘要都必须有对应可见证据；不能只截一小块漂亮海面避开控件问题。
5. 首次新 UI 基线依本文建立，**不要求像素等于旧截图**。之后改动比较新基线；掩码只允许时钟等已登记区域，不遮盖溢出或文字。
6. 自动像素差异只辅助定位；任何明显重叠、截断、错误颜色语义或目标偏移即便差异比例很小也判失败。

## 29. 最终验收流程与通过门槛

### 29.1 执行顺序

以下步骤由独立复核/最终验收执行者负责。Astra 开发阶段按第 0 节交付实现和基础证据，不要求其为满足此处流程反复进行复杂自审。

1. 固定待验收提交、依赖锁、构建产物、spec 版本与浏览器/设备；从干净安装开始。
2. 运行原有正式验收入口 `npm run acceptance`，以及本次新增的 UI、权限、交互、浏览器与性能测试；保存原始日志、命令、环境。
3. 检查原有 443 项基线测试的语义去向。允许因拆分/合并/替换样式正则改变数量，但需迁移清单证明未减少规则与信息权限覆盖；不以数量增加冒充质量。
4. 按第 25～27 节完成视口/浏览器/角色/状态矩阵，采集证据；对每个需求填最终报告。
5. 将 P0/P1 全部修复后复验受影响项和必要主链路；最后一次有效测试对应最终提交，不能用早期日志证明后续变更。
6. 进行最终全流程演示：新开局、部署、掷骰、正常行动、三人分结果、断线恢复、最终齐射、结算复盘、再来一局、离开、教程与设置。

### 29.2 一票否决项

以下任一出现即本次不通过，不能以“其他测试全绿”抵消：

- 隐藏单位、HP、结算、侦察具体坐标/数量或其他防守方私密结果泄露。
- 客户端通过改版改变伤害/资源、首雷达、合法范围、三人同步成本、胜负或终局顺序。
- 双击/重试/重连导致重复执行、错误扣弹、旧目标提交或错误房间状态覆盖。
- 在必测视口无法部署、选点、确认、关闭浮层、恢复或退出。
- 必要文本靠极小字/省略号掩盖，目标被挡住，视觉格与点击格错位。
- 只重做战斗演示，其他主流程缺失；正式页面带假数据、假按钮或调试后门。
- 为“简约”隐藏关键状态/操作，或用多重框、常驻霓虹、装饰循环规避第 3.4 节，导致只在特效演示帧中符合视觉目标。
- 关键测试失败被删除、关键浏览器/真机未测被写为通过、证据与提交不一致。

服务端连接阶段已有 `CONNECTED`、`PAUSED_ONE_OFFLINE`、`PAUSED_BOTH_OFFLINE`；这些是历史命名，不应按字符串字面推断三人离线数量，使用真实离线 ID/席位列表。

倒计时：`serverNow` 是服务端毫秒；当前前端 offset 为 `Date.now() - serverNow`，推算服务端当前时间时做减法。剩余秒为向上取整并限到零。部署 180000 ms，行动 90000 ms，重连 120 秒，连续行动超时 3 次。

旧 `render()` 用 `app.innerHTML` 重建页面；同页战斗先记/后恢复地图位置；页面切换清页面滚动；随后更新阻断层和计时。旧计时更新本身遍历 `[data-deadline]` 更新文本。不要为每秒计时重建整页。

`acceptRoomState` 会配置地图、拒绝同房间更旧版本、进入部署时重置旧局、失效时关闭确认/清草稿、去重新结果/音效、更新标题/时钟/未读，并触发 render。重构时迁移其行为，不只迁移各 `renderXPage` 的 HTML。

### 32.9 Socket 事件与请求约定

事件表以 `server/socket/protocol.js` 和 gateway 为准。所有成功 ack 为 `{ok:true,data:{...}}`；错误为 `{ok:false,error:{code,message,details}}`。前端 `emitRequest` 已解包 `response.data`；不要再多取一层 data，亦不要把原始 ack 当 view。

| 客户端事件 | 已有请求语义 |
| --- | --- |
| `client:ping` | 应答/协议检查 |
| `room:create` | nickname、maxPlayers、roomMode、mapSize；bot_duel 才带 botDifficulty |
| `room:join` | roomCode、nickname |
| `room:resume` | roomCode、reconnectToken，来自本机私密存储 |
| `room:sync` | 请求最新安全状态；已有包装可用空 payload |
| `room:leave` | expectedVersion |
| `deployment:submit` | expectedVersion、deployment 数组 |
| `deployment:ready` / `deployment:cancel-ready` | expectedVersion |
| `match:roll-die` | expectedVersion |
| `action:submit` | expectedVersion、intent（见下例） |
| `final-salvo:submit` | expectedVersion、decoyId |
| `match:surrender` | expectedVersion |
| `rematch:request` / `rematch:cancel` | expectedVersion |

服务端事件只有现有 `system:ready`、`room:session`、`room:state`、`room:error`。ready 含 stage/protocolVersion；session 用于取得身份与重连凭证；state 是每人安全快照。

```javascript
// 形状示例：使用真实当前值，不将示例 ID 固定进正式代码
await emitRequest("action:submit", {
  expectedVersion: room.stateVersion,
  intent: {
    actionId: draft.actionId,
    actionType: draft.selectedAction,
    sourceId: source.id,
    targetPlayerId: draft.targetPlayerId,
    target: { kind: "cell", coordinate: "B3" }
    // 或 {kind:"row", row:"B"} / {kind:"column", column:6}
  }
});
```

三人仍发一次相同形状意图，由服务端对仍在局目标同步结算。`targetPlayerId` 在请求中存在不等于“只攻击该人”；UI 必须解释同步语义。

当前请求超时默认 8000 ms。`ensureStateVersion` 先等待新快照约 1500 ms，随后 `room:sync`。旧包装的 timeout 表示结果未知，不能确定没发生。新版 CMD-09～CMD-14 要求保留稳定 actionId、先同步后决定，不盲目生成新 ID 重试。

部署提交是两步：本地完整校验；布局摘要有变化时先 submit，等待新版本，再带新 expectedVersion ready。投降并离开同理先等待结算，再以新版本 leave。不能并发发两个依赖旧版本的请求。

### 32.16 GPT 生图的本项目使用说明

目标是满足简约高级科幻风格所需的缺口，优先明确“资源用途→实际显示尺寸→透明/可平铺要求→文件位置”，再调用工具。无需先生成大量候选方案或反复自我评审。

适合生图：无信息海面/远景、低对比氛围、局部透明粒子/冲击、少量视觉参考。不适合整页位图：按钮文案、HP读数、倒计时、格子坐标、交互地图、复杂设置表单。

可复用提示词骨架：

```text
用途：OCEAN 浏览器回合制海战的[海面纹理/局部透明特效/非交互氛围背景]。
方向：简约、高级、科幻舰队控制台；深空海军蓝与克制青色，细节精致，低视觉噪声。
构图：[俯视/平铺/主体区域与安全留白]；实际显示范围[填写]。
避免：文字、数字、Logo、水印、假雷达点、目标标记、网格、未经授权的敌舰/情报。
输出：[透明背景或不透明]；[分辨率/比例]；若纹理需可平铺；单项资产独立文件。
```

调用后一次基本查看：用途是否吻合、透明/边缘是否正确、有无文字/假目标、实际尺寸是否可识别；明显不合格则针对问题修正。再登记、压缩到运行格式、代码集成。复杂材质/跨主题/性能/逐帧复核交给独立验收，不让Astra在生图候选之间无限打分循环。
